The core and the task

What main adds on top of master, why each piece is there, and what was deliberately left alone.

3 August 2026 · main = master@6573b7f + this · 277 self-tests green

read this first

main is not a competing implementation. It is master as of 6573b7f — every line of it — plus the pieces of the v6 architecture that master did not yet have. mapping_layer.py, app.html and engine_adapter/ are byte-for-byte master's.

Five files differ: spec_compiler.py, profile_generator.py, llm_profile.py, server.py, README.md. One file is new: task_library.py, shipped into both service packages the way function_library already is.

Every profile master can compile produces a byte-identical SPEC. That was checked against master's own compiler rather than assumed — see verification.

1 · the catalog

Two tables became one

The service that WRITES a task and the service that LOWERS it were each carrying their own description of the same seven questions, with nothing forcing them to agree.

before removed

Two files, two vocabularies, no link.

// spec_compiler.py
CONTRACT = {
  "forecast": {"keys": (0,1),
     "time_from": "R", "targets": "R",
     "features": "P", "validity": "P"},
  ... six more rows ...
}

// profile_generator.py
CLOCKED_KINDS = ("forecast", "anomaly")
KNOWN_KINDS   = ("forecast", "anomaly",
   "classify", "cluster", "regress",
   "recommend", "rank")

after added

One row per engine, in a CSV with an identical embedded fallback — the same pattern as the function and derive catalogs.

// task_library.py, both services
kind,requires,permits,keys_min,keys_max
forecast,clock|target,keys|covariates,0,4
detect_anomaly,signal,clock|keys|cov…,0,4
classify,label|keys,clock|covariates,1,4
regress,target|keys,clock|covariates,1,4
cluster,keys,clock|covariates,1,4
recommend,keys|signal,covariates,2,2
rank,keys|signal,covariates,2,2

// the generator no longer keeps its
// own list — it derives one:
CLOCKED_KINDS = tuple(k for k in kinds()
  if "clock" in plan(k)["requires"])
the drift this caught, immediately

The hand-written tuple said CLOCKED_KINDS = ("forecast", "anomaly") — that anomaly detection requires a clock. The catalog says it only permits one: detect_anomaly requires a signal, nothing more.

They had disagreed for as long as both existed, because nothing made them agree. Deriving the tuple made the contradiction a test failure on the first run. The consequence is real: "find outliers in customer spend" over a table with no date column is a legitimate question, and it used to be refused.

what a kind actually decides

Everything downstream. Whether a clock exists at all, how many key columns to pick, which field names what is being predicted, and whether anything is predicted at all.

A field a kind has no concept of is an error, not an ignored hint. An optional field would mean every engine had to know to skip it, and nothing would catch a recommender that set a grain by mistake. So task.horizon is rejected by name, and so is a clock on a recommend.

2 · the split

A metric stopped having a role

One question sorts every field: with no engine attached, does this still describe something real about the data? If yes it is a fact and belongs to the core. If it goes meaningless, it was describing the question.

master

The question is spread across the metric, a time block, an x-deep block and a partial task.

{
  "metrics": [
    { "name": "rentals",
      "function": "sum",
      "measure": "cnt",
      "role": "target" },
    { "name": "promo",
      "function": "max",
      "measure": "on_promo",
      "role": "feature",
      "availability": "known_ahead" }
  ],
  "time": {"event":"dteday","grain":"day"},
  "x-deep": {"series": "store"},
  "task": { "kind": "forecast",
            "keys": [ … ] }
}

main added

The core says what things mean. The task says what is asked of them.

{
  "metrics": [
    { "name": "rentals",
      "function": "sum",
      "measure": "cnt" },
    { "name": "promo",
      "function": "max",
      "measure": "on_promo" }
  ],
  "dimensions": [{"name": "store"}],

  "task": {
    "kind":   "forecast",
    "clock":  {"event":"dteday","grain":"day"},
    "keys":   ["store"],
    "target": "rentals",
    "covariates": [
      {"metric":"promo",
       "availability":"known_ahead"} ]
  }
}
why the role had to move, rather than just be renamed

A role stamped on a metric means the metric's schema grows every time an engine is added. A recommender wants role: "signal"; a classifier wants role: "label"; the enum creeps outward forever, and every existing profile has to be re-read whenever it does.

Inverting it — the task holds a pointer to a metric — freezes the metric schema permanently. task_library is what says which pointer a given kind uses, so adding an eighth engine that predicts something called a ranking is a catalog row, not a change to how a metric is written.

the three pointers, and why a clustering has none

target — a numeric forward-looking question. signal — a value scored when there is no ground-truth label. label — a categorical prediction. They differ only in what the engine calls the thing; at most one is in any kind's requires.

cluster has none at all, and that is a complete answer rather than a missing one. It requires keys and permits covariates, so every metric rides alongside and nothing is nominated. Handing a clustering a target now fails with "kind 'cluster' has no concept of 'target'".

3 · the migration

A flat profile still compiles, byte for byte

The split is only adoptable if nothing has to adopt it on the same day. A profile carrying time / x-deep / role is not a second code path — it is the same task, spelled the old way.

lift_task(profile) added

Master's task_field() read one field from either shape. This completes the idea: it produces the whole task, so everything after it reads one vocabulary and never asks which shape came in.

task, lifted = lift_task(profile)   # kind, clock, keys, pointer, covariates
plan, kind, pointer, pointed = task_library.check(task, metric_names)
#            ^ the catalog is the contract, for both shapes alike

for ob in walk(profile, task, binding, lib, naming):   # reads the task, never
    …                                              # the flat blocks
what the report tells you

The compile report carries lifted_from_flat: true when the old spelling was used. That is not a warning — a flat profile is entirely valid — it is the signal that a producer upstream has not migrated yet, which is the thing you actually want to track during a rollout.

It also echoes the lifted task, so you can see exactly what the compiler understood the question to be without re-deriving it by hand.

verified, not asserted

Master's compiler was loaded side by side with main's and fed the same profiles: x-deep+time+role, two targets with a known_ahead covariate and filters, a past_only covariate, master's own task block, a row_number classification, a clustering, and the legacy anomaly spelling — each under both v1 and logical naming, with and without available_from.

Every SPEC matched, character for character. The only divergences were profiles master refused to compile at all; see the three behaviour changes.

4 · the front of the pipeline

The goal text picks the question — all seven of them

The model reads the sentence and chooses the engine. A keyword scaffold picks one too, in a fixed order, and that is the fallback — so an outage still produces a correctly-shaped task.

the engine table is generated into the prompt added

From task_library, never written out by hand.

// what the model is shown, verbatim
ENGINES (the only questions that can be asked; pick exactly one)
  classify
      Predict a categorical label per entity
      requires: label, keys
      accepts:  clock, covariates
      keys:     1-4
  … six more, straight off the catalog …
what this replaced, and why it mattered

The prompt used to carry the rules as prose: "kind forecast and anomaly require a time column; recommend, cluster, classify, regress and rank must not have one." By the time it was read, that was wrong against the catalog on three of the seven — classify, cluster and regress all accept a clock — and it spelled detect_anomaly as anomaly, which is not a value the enum would accept.

The same three rules were hardcoded a second time in the reply validator, so a correct answer from the model would have been rejected. Both now read the catalog. Adding an engine reaches the model in the same commit it reaches the compiler.

the model is never asked to learn three names for one idea

An engine's pointer is target, signal or label depending on the row. The model marks what is predicted with role target and everything else feature, and the lift renames it to whichever the kind uses — the same path a legacy profile takes. One fewer thing to get wrong, and it reuses code that was already tested.

goalkindwho scaffolds it
forecast next quarter's revenueforecast kept master's clocked path

a permitted clock is not an assumed clock

A kind that requires a clock always gets one. A kind that merely permits one gets it only if the goal asks for time — otherwise "segment customers" would quietly become "segment customers per month", which is a different question with a different answer.

Adding each month to that same goal puts the clock back. Both are tested.

the column the goal named outranks any shape heuristic

"segment customers" keys on cust_id rather than on whatever column happens to sit first and look dimension-shaped. The match is on whole words of the column name, so cust_id is named by "customers" while generic fragments — _id, _nbr, code — prove nothing on their own.

5 · restraint

What was deliberately left alone

Master's commit 6573b7f landed three things that are better than what the v6 document describes, or better than what an earlier draft of this work had. They were kept, and in one case a worse version was thrown away.

label() kept

Folds a categorical column into integer class ids, with the id-to-name mapping in frame metadata.

An earlier draft of this work solved the same problem by letting first/last pass strings through untouched. That was worse on both counts: it put raw text in the frame, and it opened the text path on two functions instead of one. It was discarded.

row_number kept

A key whose value is the row's position, for data already one row per thing with no id column — iris, wine, sonar, most classic sets.

Also master's insight that which keys may omit from is a property of what the derive RETURNS, not of the string "bin:". That naming convention was load-bearing in four places of the draft this replaced.

availability, not anchor kept

v6 renames this field to anchor: event|arrival. Master's own comment already makes v6's argument for it — per column, "a fact about the DATA", absent meaning what targets always had.

So this is a naming difference, not a missing feature, and renaming it would churn 170 green tests to buy nothing.

run_config was kept over v6's earlier run_config_hint for the same reason — master's is the later idea, and it already does what v6's stage 5 asks for. It gained two fields: pointer (which of target/signal/label the question used) and known_ahead.

mapping_layer.py was not touched at all. Nothing it does was missing.

6 · judgement calls

Three places where behaviour differs from master

Each is a case master rejected and main now accepts. None changes a SPEC master could already produce.

whatmastermainwhy
changed regress with a clock Rejected — the table forbade time_from by hand Compiles The catalog permits it, and regression over time is a real question. The hand-written rule was the accident.
changed validity on a clockless kind Hard error, per kind: classify / cluster / recommend / rank / regress all forbade it Emitted when the task has a clock; omitted with a warning when it does not A leakage guard needs periods to re-file between. The per-kind rule also refused it to a clocked classification, which legitimately wants one.
changed a key naming an undeclared dimension Warning in the compiler Still a warning in the compiler; a hard error at finalize The catalog would make it an error everywhere, but by compile time the binding is in hand and the key resolves to a real column — refusing would reject a profile that works. The gate belongs where a human is about to sign.
two bugs the integration surfaced, both now covered

A row_number key never reached task.keys. It has no from, so the name-extraction skipped it and the catalog was told a classification had no keys at all. It identifies a row without being a dimension, so it now contributes its derive name.

finalize dropped authored key objects. It read task.keys in preference to a top-level keys[], so running it over its own output discarded the objects — and with them the only spelling a row_number key has. Every iris-shaped classification would have broken. It now uses the same precedence the compiler does.

Neither was reachable from master's own tests, because master's generator never produced a task and its compiler never round-tripped one.
