The shape, at a glance

Five slots. Only keys and aggregates are required.

{
  "keys":       [ … ],   // what identifies one output row
  "aggregates": [ … ],   // the numbers in that row
  "derives":    [ … ],   // calendar columns off a binned key
  "filters":    [ … ],   // which raw rows count at all
  "validity":   { … },   // when a row became knowable

  // plus, when the clock or the inputs need naming:
  "time_from":   "…",     // the column a bin: key reads
  "sources":     [ … ],   // several inputs, joined on the clock
  "source_from": "…"      // the column tagging each row's source
}

Every column in the output frame is declared here by name. Nothing is implied, nothing is prefixed automatically, and there is no reserved column.

the one rule worth internalising A field belongs in the SPEC if changing it changes the frame. Grain, keys, functions and anchors all move cells, so they live here. Horizon, season length, engine and which column you predict move nothing, so they live in the run config.

One complete example

Supplier concentration by category, quarterly, with a leakage guard. This is real output from datasets/awards.csv.

{
  "time_from": "action_date",
  "validity": { "arrival_from": "reported_dt" },

  "keys": [
    { "name": "category", "from": "product_category" },
    { "name": "period",   "via":  "bin:quarter" }
  ],

  "aggregates": [
    { "name": "spend", "using": "sum", "of": "dollars_obligated" },
    { "name": "hhi",   "using": "hhi", "of": "dollars_obligated",
      "by": "recipient_parent", "anchor": "arrival" }
  ],

  "derives": [
    { "name": "q", "scope": "key", "from": "period", "via": "quarter_of_year" }
  ]
}
category      period    spend         hhi           q
aerospace     2024-Q1   100000000.0   4600.0        1
aerospace     2024-Q2   104000000.0   4016.272189   2
aerospace     2024-Q3   102000000.0   6388.021737   3
aerospace     2024-Q4   null          10000.0       4
it_services   2024-Q1    20000000.0   2500.0        1
…

Read the column order straight off the SPEC: keys first, then aggregates, then derives, each under the name you gave it.

That 2024-Q4 row is the interesting one. There is no Q4 spend, because no award happened in Q4. The row exists because one September award was not reported until 30 October, and hhi is anchored to arrival — so its value was re-filed forward into the quarter where a forecaster would first have had it. More on that below.

keys — what a row is

Rows sharing the same key values are aggregated together. This is the GROUP BY. Order matters twice: it is the composite-key order and the frame's sort order.

name *
The output column name for this key.
from
The column to read. Omit only on a bin: key, which then bins whichever column each source declared as its clock.
via
A derive applied before grouping. A bin: derive turns a date into a time bucket.
prefix
Prepended to this key's values. "store_" turns 12 into store_12.
aliases
Rewrite raw values before grouping — merging subsidiaries under a parent, say. A list of {value, replace_with}.
// a plain key — one row per customer
{ "name": "customer", "from": "cust_id" }

// a time key — this is how a clock enters a frame
{ "name": "period", "via": "bin:quarter" }

// two plain keys — a recommendation grid
{ "name": "customer", "from": "cust_id" },
{ "name": "item",     "from": "item_sku" }

time is not a special slot There is no time_grain field. A clock is just a key with a bin: derive, which is why a frame can have two keys, or five, or none that are temporal at all. A cross-sectional question simply has no bin: key — and then time_from is not required either.

aggregates — the numbers

One entry per output column that is not a key.

name *
The output column name. Must not collide with a key.
using *
A function from the catalog, applied within each key bucket.
of
The measure column the function reads. Required whenever the catalog row says needs: measure; omitted for count.
by
The entity column to form shares over. Required when the catalog row says needs: entity — today that means hhi and top_share.
anchor
event (default) or arrival. See below.
source
Only with multiple sources, and only when the function reads no column (a bare count) so the source cannot be inferred.
// a simple sum
{ "name": "revenue", "using": "sum", "of": "amount" }

// count needs no measure at all
{ "name": "orders", "using": "count" }

// a group function totals per entity first, then reduces
{ "name": "concentration", "using": "hhi",
  "of": "dollars_obligated", "by": "recipient_parent" }

A row reaches the frame when at least one aggregate produced a value. A bucket where everything is null is dropped; a bucket with one live number and three nulls is kept, with nulls in the frame.

no roles here There is no target or feature. Which column an engine predicts is a per-run decision, and choosing differently must not move a frame cell — so it lives in the run config. A SPEC that carries role or availability is rejected, with a message pointing at the right home.

anchor — which bucket a value belongs to

The subtle one, and the only place a per-column setting quietly changes where data lands.

Two timestamps matter for any fact: when the thing happened, and when you found out. Anchor says which of those a column is filed under.

anchormeansuse for
event
(default)		 The value describes that period, whenever it arrived. Labels — Q1 sales were Q1 sales. Also anything already knowable at the time.
arrival The value belongs to the bucket where it became knowable. If that is later than the event bucket, it is re-filed forward. Covariates you only learn in arrears, where using them earlier would be looking into the future.

Anchor only bites when validity.arrival_from is set. Without an arrival column there is nothing to compare against, and everything files by event time.

why this matters more than it looks Getting it wrong produces lookahead bias, which does not crash and does not warn — it makes backtests look better. Nobody investigates a model that validates well. It surfaces months later as a production model that has never once matched its evaluation.

Because anchor is per column rather than per role, you can aggregate the same measure twice and get both views in a single pass:

{ "name": "as_happened", "using": "max", "of": "promo", "anchor": "event"   },
{ "name": "as_known",    "using": "max", "of": "promo", "anchor": "arrival" }

A promo dated 20 July but not knowable until 5 September lands in as_happened for July and in as_known for September. The count of moved values is reported as metadata.leakage.features_refiled_forward.

derives — calendar columns

Computed from a binned key, not from the rows. Always defined, so they never decide whether a row is emitted.

name *
The output column name.
via *
A derive from the catalog.
scope
key (default) — runs once per output row. row is catalogued but not built yet; asking for one tells you so.
from
Which binned key to read. Defaults to the time key.
{ "name": "q", "scope": "key", "from": "period", "via": "quarter_of_year" }

filters — which rows count

Row-level predicates, ANDed together.

of *
The column to test.
using
One of equals, notEquals, greaterThan, lessThan, contains, isEmpty, isNotEmpty. Defaults to equals.
value
The comparand. Unused for the two emptiness tests.
applied_upstream
true means a database already ran this predicate: keep it declared, do not re-run it.
{ "of": "awarding_agency", "using": "equals",      "value": "DoD"   },
{ "of": "dollars_obligated", "using": "greaterThan", "value": 25000 },
{ "of": "cancelled_dt",    "using": "isEmpty" }

Predicates should be declared here even when a database executes them. The SPEC is the reviewed artefact — a scoping decision that changes the numbers has to stay visible in it, and applied_upstream is how you get pushdown without losing that.

known defect greaterThan and lessThan compare numerically. A date comparand does not parse as a number, so a date-range filter silently matches nothing. Filter dates with a bin: key or upstream until the operator catalog carries an operand type.

validity — the leakage guard

Declares which column says when a row became knowable, as distinct from when the thing it describes happened.

arrival_from
The arrival-timestamp column. Enables anchor: "arrival"; without it, anchor has nothing to compare against and does nothing.
"validity": { "arrival_from": "reported_dt" }

Worked through, at quarterly grain:

a shipment happened      2024-02-14   → event bucket   2024-Q1
it was reported          2024-04-08   → arrival bucket 2024-Q2

anchor: "event"    → lands in 2024-Q1
anchor: "arrival"  → lands in 2024-Q2   re-filed; Q1 never sees it

why this cannot live anywhere else The decision needs both timestamps for an individual row, at the moment it is placed in a group. After aggregation the bucket holds a number and the per-row provenance is gone — no later stage can reconstruct it. A plain join upstream destroys it in the other direction, attaching a value to a row that predates knowing it. This is the reason the mapping layer exists instead of a GROUP BY.

Multiple sources

Optional. With one input you can skip this section entirely and just set time_from.

time_from
The clock column, for a single source or as the default for sources without their own. Required only if some key uses a bin: derive.
sources[].id *
The source's id, used to qualify columns as <source>.<column>.
sources[].time_from
That source's own clock column.
sources[].available_from
That source's own arrival column.
source_from
The column tagging each raw row with its source id. Required as soon as there is more than one source.
"source_from": "src",
"sources": [
  { "id": "power",   "time_from": "period" },
  { "id": "weather", "time_from": "time"   }
],
"aggregates": [
  { "name": "y_power", "using": "mean", "of": "power.value_MWh"    },
  { "name": "y_temp",  "using": "mean", "of": "weather.temperature_c" }
]

Sources are aligned on the shared time bucket. Where one source cannot supply a key — weather has no respondent column, say — its values broadcast onto every row that agrees on the keys it can supply. A bucket with no matching partner emits null rather than disappearing, and the count is reported as metadata.join.gaps.

The catalogs

Both are data files with an identical embedded fallback, so a name is never guessed and never silently defaulted.

Functions — function_library

usingshelfneedswhat it does
sumcoremeasureAdd a measure up
meancoremeasureAverage a measure
mincoremeasureSmallest value
maxcoremeasureLargest value
firstcoremeasureFirst value, by input order
lastcoremeasureLast value, by input order
countcore—Count the rows in the bucket
hhisupply-chainmeasure, entity Herfindahl-Hirschman index: sum of squared percent shares
top_sharesupply-chainmeasure, entity Largest single entity's percent share

The needs column is not documentation — it is what generates the SPEC's fields. Adding a catalog row with a new need adds a new field to the aggregate, with no change to the compiler's branching.

A group function does two passes inside one bucket: it totals of per distinct value of by, then reduces those entity totals to one number. That is why HHI nets deobligations per vendor before computing shares.

bucket derives go on a key and return a label plus a sort value. scalar derives go in derives[] and read a bucket. Ask for a name that is not here and you get an error listing everything that is — never a default.

What the SPEC does not contain

Apply the test: change it, does the frame change? If no, it does not belong here.

not in the SPECwhylives in
role Which column is predicted is a per-run choice. Same frame either way. run config
availability Whether a covariate is usable for future rows. Once anchor exists, this moves no cells. run config
horizon How far ahead to predict. The frame is history; the adapter builds the future scaffold. run config
season_length,
quantiles, model		 Fit parameters. They never touch a row. run config
column naming unique_id/ds for Nixtla, item_id/timestamp for AutoGluon — same numbers, different labels. engine dialect
kind forecast, cluster, regress… Needed to validate that a question is coherent, but not to build the frame. profile

The payoff is worth stating plainly: the frame is a pure function of the SPEC. Twenty runs sweeping horizon, season and model read one cached frame. Two engines compared over one frame saw identical numbers, so the comparison is honest.

The run config

Everything that configures the engine call and touches nothing in the frame. It never reaches the compiler or the mapping layer.

status Not built as a service yet. It exists in the pipeline lab as a browser-side panel that is echoed back untouched, which is how you verify the purity claim above. The shape below is the intent, not a shipped contract.

{
  "engine":        "nixtla",          // selects the dialect
  "model":         "AutoETS",
  "target":        "concentration",   // which aggregate to predict
  "covariates":    ["x_promo"],       // default: everything else
  "known_ahead":   ["x_promo"],       // usable for future rows
  "horizon":       8,
  "season_length": 4,
  "quantiles":     [0.1, 0.5, 0.9],
  "backtest":      { "windows": 3, "step": 1, "refit": false },
  "metrics":       ["mase", "smape"],
  "seed":          42
}

The compiler does not emit this, but it does report a suggestion. A profile says which metric was meant to be the target; that comes back as metadata.run_config_hint with target, covariates and known_ahead, for the engine side to prefill. Overriding it is then an explicit act that recompiles nothing.

Some run configs are nonsense against some SPECs, and the adapter is where that gets caught: a season length of 52 against a quarterly grain, a horizon with no bin: key to project along, two entity keys against an engine that takes one series id. One check has to look at data rather than documents — whether a known_ahead covariate actually extends far enough forward to cover the horizon.

Coming from a v1 SPEC

Old specs still run, untranslated by you. The mapping layer converts them on the way in, which is why v1's column names are simply what the translation writes.

v1now
series_from: "store" keys: [{ name: "series_id", from: "store" }]
time_grain: "week" keys: [{ name: "t", via: "bin:week" }]
series_prefix / series_aliases prefix / aliases on that key
targets: [{ fn, measure, entity }] aggregates: [{ using, of, by }]
features: [{ … }] aggregates, plus derives for the calendar ones
availability: "past_only" anchor: "arrival"
availability: "known_ahead" anchor: "event" (the default — omit it)
role: target / feature gone — the run config picks the target
filters[].column / .operator filters[].of / .using

Two differences to expect. A v1 spec still gets the old metadata.targets and metadata.features lists; a v2 spec gets a single metadata.aggregates with anchors instead. And v1 quietly defaulted a missing grain to weekly — v2 has no default anywhere, so a name that is not in a catalog is an error that lists the catalog.
